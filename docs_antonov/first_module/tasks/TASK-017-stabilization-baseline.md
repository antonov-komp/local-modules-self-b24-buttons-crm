# TASK-017: Stabilization baseline — аудит и стабилизация текущих четырёх типов кнопок

**Дата создания:** 2026-10-29  
**Статус:** Новая  
**Приоритет:** Высокий  
**Исполнитель:** Bitrix24 Программист / аналитик (коробка, D7 + Vanilla JS)

## Цель

Зафиксировать и стабилизировать текущую реализацию `my.bpbutton` на baseline `28f73db` перед архитектурным рефакторингом и дальнейшим добавлением action type.

TASK-017 **не добавляет новый тип кнопки**. Её задача — доказать работоспособность существующих режимов, устранить очевидные дефекты и подготовить проект к безопасному TASK-018.

## Исходное состояние

В `main` реализованы четыре режима:

1. `url`
2. `bp_launch`
3. `bp_launch_with_params`
4. `bp_launch_with_button_params`

TASK-016 была реализована и влита в `main` через PR #2, но автоматические тесты по PR не выполнялись. Поэтому требуется отдельная регрессионная приёмка.

## Scope

### 1. Regression / smoke существующих режимов

Проверить каждый action type в коробочном Bitrix24:

- корректный рендер кнопки в CRM-карточке;
- корректный `ENTITY_ID`, `ELEMENT_ID`, `FIELD_ID`;
- отсутствие сохранения карточки при обычном клике кнопки;
- обработку активности `ACTIVE`;
- проверку Bitrix session;
- CRM read access;
- работу success/error response;
- бизнес-логирование результата.

### 2. `url`

Проверить:

- получение `HANDLER_URL`;
- добавление context query-параметров;
- открытие SidePanel;
- `TITLE` и `WIDTH`;
- отсутствие регрессий для относительных и абсолютных URL, которые уже разрешены текущей валидацией.

### 3. `bp_launch`

Проверить:

- выбранный `BP_TEMPLATE_ID`;
- корректный тип CRM-сущности;
- `CCrmBizProcHelper::getBpStarterConfig()`;
- права пользователя на запуск;
- успешный запуск БП;
- ошибку для удалённого/невалидного шаблона.

### 4. `bp_launch_with_params`

Проверить:

- `PARAM_NAME`;
- `PARAM_TITLE`;
- popup ввода значения;
- запрет пустого значения;
- передачу значения в `CBPDocument::StartWorkflow()`;
- права пользователя;
- success/error UX.

### 5. `bp_launch_with_button_params`

Проверить:

- загрузку `PARAM_BUTTONS` из JSON;
- отображение вариантов;
- запрет значения, отсутствующего в server-side списке;
- передачу выбранного значения в БП;
- защиту от повторного клика;
- негативные случаи: пустой список, дубли, удалённый шаблон, отсутствие прав.

## Технические исправления TASK-017

### A. Исправить fallback текущего пользователя в ButtonHtmlRenderer

Файл:

- `local/modules/my.bpbutton/lib/UserField/ButtonHtmlRenderer.php`

Текущее поведение при отсутствии `$GLOBALS['USER']` может получить первый ID из `UserTable`.

Нужно:

- удалить fallback через `UserTable::getList()`;
- при невозможности определить текущего пользователя возвращать `userId = ''` или `0`;
- подтвердить, что backend продолжает определять пользователя самостоятельно и не доверяет DOM `data-user-id`.

### B. Проверить бизнес-логирование

Файлы:

- `lib/Controller/ButtonController.php`
- `lib/Service/ButtonService.php`
- `install/js/my.bpbutton/button.js`

Нужно проверить, не создаются ли двойные бизнес-логи одного пользовательского действия из-за одновременного логирования backend и frontend/AJAX-слоя.

Результат проверки должен быть зафиксирован документально. Если дублирование подтверждено — определить единственный authoritative слой для business audit.

### C. Зафиксировать стратегию миграций БД

Сейчас миграции колонок присутствуют как минимум в:

- `local/modules/my.bpbutton/install/index.php`;
- `local/modules/my.bpbutton/lib/EventHandler.php`.

TASK-017 должна:

- инвентаризировать все изменения схемы `my_bpbutton_settings`;
- описать текущую схему как baseline;
- определить безопасную стратегию обновления существующих коробочных установок;
- подготовить перенос миграций из runtime.

На этом этапе допустимо оставить реализацию переноса на TASK-018/отдельную refactor-task, если изменение схемы требует отдельной процедуры обновления, но после TASK-017 не должно оставаться неопределённости, как это будет сделано.

### D. Проверить cache semantics SettingsRepository / SettingsResolver

Проверить поведение static cache после изменения настроек в рамках одного HTTP-запроса.

Если чтение после `save()` / `toggleActive()` потенциально может получить устаревшее значение, определить место для `clearCache()` либо стратегию invalidation.

### E. Синхронизировать документацию

Обновить:

- `TASK-LATEST.md`;
- TASK-016 статус;
- обзор текущих action type;
- README/архитектурные документы, если они описывают только исходный URL/SidePanel-сценарий.

## Что НЕ входит в TASK-017

- добавление пятого action type;
- полный переход на Action Handler architecture;
- масштабный redesign административной страницы;
- изменение бизнес-семантики существующих четырёх режимов;
- переход на облачный Bitrix24/REST-приложение.

## Ожидаемый результат

После TASK-017 проект должен иметь подтверждённую стабильную функциональную базу из четырёх action type и понятный технический долг.

Следующий архитектурный этап — TASK-018 с разделением action-specific логики на отдельные обработчики и выносом общих сервисов запуска БП, логирования и маршрутизации.
