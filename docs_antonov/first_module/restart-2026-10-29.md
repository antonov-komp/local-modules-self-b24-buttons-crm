# Restart 2026-10-29: текущая точка проекта и план развития

**Проект:** `my.bpbutton` — локальный модуль кнопок для CRM Bitrix24.  
**Целевая платформа:** только коробочный Bitrix24 с доступом к `/local/`, D7 ORM и серверному PHP-коду.  
**Базовый commit:** `28f73db` (`main`).  
**Рабочая ветка перезапуска:** `restart/project-audit-2026-10-29`.

## 1. Зачем зафиксирован этот restart

Проект был восстановлен после паузы и повторно просмотрен по фактическому коду, а не только по старой документации. Цель текущего этапа — не добавлять очередной тип кнопки, а стабилизировать уже существующую платформу и подготовить её к дальнейшему расширению без накопления монолитной логики.

`28f73db` принимается как контрольная исходная точка: локальная и удалённая ветка `main` совпадают, рабочее дерево чистое, TASK-016 уже включена в `main` через PR #2.

## 2. Что модуль умеет сейчас

Пользовательское поле `bp_button_field` поддерживает четыре режима действия:

1. `url` — открыть настроенный URL в SidePanel.
2. `bp_launch` — запустить выбранный бизнес-процесс.
3. `bp_launch_with_params` — запросить строковое значение и передать его в параметр бизнес-процесса.
4. `bp_launch_with_button_params` — показать набор UI-кнопок, передать выбранное значение в параметр и запустить бизнес-процесс.

Дополнительно модуль содержит:

- административный реестр и форму настройки;
- ORM-таблицы настроек и логов;
- проверку CRM-доступа и Bitrix session;
- аудит кликов и результатов;
- поддержку CRM и смарт-процессов;
- опцию скрытия стандартной вкладки «Бизнес-процессы» для сущности;
- отдельные JS-слои `button.api.js`, `button.state.js`, `button.utils.js`, `button.sidepanel.js`, `button.js`.

## 4. Найденный технический долг

### 4.1. Runtime-миграции в EventHandler

`EventHandler::onMainProlog()` при обычных запросах проверяет наличие колонок и может выполнять `ALTER TABLE`. Аналогичная миграционная логика уже присутствует в `install/index.php`.

Это создаёт двойную ответственность и связывает runtime с изменением схемы БД.

Целевое состояние:

```text
install / update
    -> управляемые миграции схемы

runtime
    -> никаких ALTER TABLE
```

### 4.2. ButtonService стал центральным монолитом

`ButtonService` одновременно:

- маршрутизирует `ACTION_TYPE`;
- формирует runtime-конфигурацию;
- запускает бизнес-процессы;
- валидирует BP-параметры;
- формирует URL и context;
- проверяет BP-операции;
- пишет бизнес-логи;
- очищает сообщения логов от чувствительных данных.

Для четырёх типов это ещё управляемо, но дальнейшее добавление action type будет увеличивать связанность класса.

### 4.3. BpButtonUserType перегружен

Класс одновременно является адаптером Bitrix UserField, содержит callbacks, настройку subtype, административный HTML и часть логики чтения настроек. Рендер кнопки уже вынесен в `ButtonHtmlRenderer`, поэтому разделение можно продолжить.

### 4.4. Некорректный fallback userId

`ButtonHtmlRenderer` при отсутствии текущего пользователя может получить первый ID из `UserTable`. Такой fallback семантически неверен. Backend всё равно должен определять фактического пользователя серверно; frontend context не должен подставлять произвольного пользователя.

Целевое поведение: при отсутствии текущего пользователя передавать `0`/пустое значение и не имитировать чужой userId.

### 4.5. Диспетчеризация action type дублируется в backend и frontend

`ButtonService` выбирает обработчик по `ACTION_TYPE`, и `button.js` повторяет аналогичное ветвление. При росте числа типов оба файла будут увеличиваться одновременно.

### 4.6. Документация отстаёт от кода

TASK-016 в документации всё ещё имеет статус «Новая», хотя реализация была влита в `main`. При этом автоматические тесты для PR #2 не выполнялись, поэтому TASK-016 нельзя считать полностью принятой без регрессионной проверки.

## 5. Новая последовательность развития

### Этап A — TASK-017: Stabilization Baseline

Сначала стабилизируем существующие четыре режима без добавления нового функционального типа.

Основные направления:

- синхронизация документации с фактическим кодом;
- regression/smoke для четырёх action type;
- исправление fallback userId;
- проверка двойного/избыточного логирования frontend/backend;
- фиксация текущей схемы БД и стратегии обновлений;
- подготовка переноса runtime-миграций из `EventHandler`;
- проверка совместимости CRM и смарт-процессов;
- фиксация известных ограничений.

### Этап B — TASK-018: Action Architecture

После стабилизации перейти от централизованного `ButtonService` к обработчикам действий.

Целевой ориентир:

```text
Action/
  UrlAction
  BpLaunchAction
  BpLaunchWithParamsAction
  BpLaunchWithButtonParamsAction
```

Общие сервисы отдельно:

```text
BpWorkflowRunner
ClickLogger
ActionRegistry / ActionResolver
```

`ButtonService` после рефакторинга должен оставаться тонким orchestration-слоем либо быть заменён registry/resolver-моделью.

### Этап C — последующие типы кнопок

Только после стабилизации и Action Architecture добавлять новые режимы. Каждый новый action type должен подключаться как отдельный обработчик, а не расширять большой `if/elseif` в нескольких местах.

## 6. Принципы дальнейшей разработки

1. Только коробочный Bitrix24.
2. `main` остаётся стабильной веткой.
3. Любая новая функциональность идёт через отдельную TASK и рабочую ветку.
4. Сначала тестирование и фиксация baseline, потом рефакторинг, потом новые типы.
5. Runtime не должен изменять схему БД.
6. Backend не доверяет `userId`, переданному из DOM/JS; текущий пользователь определяется сервером.
7. Общие механизмы прав, логирования и запуска БП не должны дублироваться между action type.
8. Документация обновляется вместе с кодом.
